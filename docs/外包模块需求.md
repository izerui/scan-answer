# 答题卡识别模块 · 开发需求

- 版本：V1.0
- 日期：2026-11-09
- 合作方式：**委托开发**。需求方出资，开发方按这份需求开发；做完后全部源代码和文档交付需求方，以后由需求方自己维护、升级。

> 这份文档只写主要功能、整体逻辑和要达到的效果。具体怎么设计、怎么实现、界面怎么做，由开发方考虑，设计阶段交需求方确认。

---

## 1. 背景

现在已经有一套**考研系统**，出题这些都在里面做，但缺一块：**用扫描仪扫答题卡，把考生答了什么识别出来**。本模块就是补这一块，识别结果交给考研系统批改。

有两种使用场景，用的是同一套客户端和扫描仪：

- **批量扫描**：考试结束后，把一场考试的答题卡成批扫完；
- **单张扫描**：学生自己写完一张卡，拿到连着客户端的扫描仪上单独扫，扫完就提交批改。这种情况零散、随时发生，可能分布在几台电脑上。

## 2. 整体结构和流程

```
 扫描客户端（Windows，可多台）              后端服务（一个）                 考研系统
┌────────────────────────┐          ┌──────────────────────┐
│ 连扫描仪扫描 / 导入图片   │  上传结果  │ 模板、结果统一存放      │   推送结果   ┌────────┐
│ 识别填涂（选项、考号等）  │ ───────▶ │ 手写识别（云端大模型）  │ ─────────▶ │  批改   │
│ 现场问题提示、重扫        │ ◀─────── │ 和考研系统对接          │            │        │
└────────────────────────┘  下载模板  └──────────────────────┘            └────────┘
```

1. **建模板**：拿空白答题卡做识别模板，存到后端。建模板放在客户端还是后端 Web 页面，由开发方定。
2. **扫描识别**：客户端从后端取模板，扫描后当场识别填涂内容；有问题当场提示、重扫。
3. **上传**：每扫完一张就上传到后端，不等整批。
4. **手写识别**：后端调用云端大模型，把填空、作文等手写内容识别成文字。
5. **交给考研系统**：后端按考研系统的接口规范，把结果提交给考研系统批改。

## 3. 主要功能

- **建模板**：各种来源、各种版式的答题卡都能做成模板；尽量自动，少让人手工画；做好后能拿样卡试识别；模板有版本管理。
- **扫描**：支持 TWAIN 的扫描仪都要能用，不绑定品牌型号；也能导入图片 / PDF；批量扫、单张扫都要顺手。
- **识别**：
  - 选择题输出选了哪个选项，区分没涂、多涂、拿不准等情况；
  - 填空、作文、解答题等手写内容识别成文字，中文、英文、数学公式都要支持；用能识别图片的云端大模型来做，在后端配置好 base URL、API Key、模型名就能用，换服务商也只改配置；
  - 结果里带上能对应到考研系统**哪个学生、哪场考试**的字段（从卡上读出）。
- **输出和对接**：输出标准的 JSON 结果和切图，格式有说明文档；按考研系统提供的接口规范对接，对接工作由开发方完成，考研系统不需要为此改动；提交失败能重试，重复提交不重复入库。

## 4. 几条底线

1. **部署简单**：客户端一个安装包，后端一个服务，正式环境私有化部署在需求方提供的云服务器上，不要复杂的部署结构。客户端通过公网访问后端，要有身份认证和加密传输。
2. **现场不能被后端卡住**：后端或网络出问题时，客户端照常扫描识别，恢复后自动补传，数据不丢不重。
3. **只识别，不判分**：判分、批改是考研系统的事。
4. **不能悄悄出错**：没把握的地方必须标出来，不能给一个看起来正常、实际是错的结果。
5. **能追溯**：每个识别结果都能找回对应的原图和切图。
6. **需求方自己能接手**：交付后需求方自己维护、升级，以后接别的系统也是需求方自己改。

## 5. 质量要求

| 项目 | 要求 |
|---|---|
| 选择题识别 | 规范填涂正确率 ≥ 99.9% |
| 学生、考试对应 | 识别不全必须标出来，不能对应错人 |
| 手写内容识别 | 按样卡实测，在验收方案里约定 |
| 现场问题检出 | 缺页、混卡、空白页 100% 检出 |
| 稳定性 | 一批几千张、几台客户端同时用都要稳定；断网恢复后不丢不重 |

## 6. 源码和维护

交付后由需求方自己维护和升级，所以：

- 技术选型由开发方自定，怎么方便怎么来，用主流、成熟的开源技术即可；不能依赖开发方的私有组件、授权或账号；
- 代码结构清楚，有自动化测试；文档齐全，需求方照着能自己构建、部署、发版；
- 新版本能平滑升级，已有模板和数据不丢；
- 源码在需求方的代码仓库里开发，或每个里程碑交一次，不能最后才一次性给。

## 7. 交付

- 全部源代码、客户端安装包、后端部署包；
- 文档：结果格式说明、部署和使用说明、开发文档；
- 测试报告；使用培训和技术交接。

**知识产权**：全部成果（含源代码、文档）的知识产权归需求方，写进正式合同；需求方可以自由修改、二次开发、用于其他系统。开发方对项目资料和成果保密。

## 8. 验收

1. 功能演示通过；
2. 用需求方提供的答题卡现场实测，达到第 5 章的指标；
3. 和考研系统跑通全流程，批量和单张两种场景都要跑；
4. 需求方开发人员照着文档能独立构建、部署、发版；
5. 至少经过一次真实使用。

具体验收方案由开发方在设计阶段拟定，需求方确认。

## 9. 进度

开发周期初步预计 1 个月，具体里程碑由开发方排期。

开发和联调阶段，开发方先在自己的环境里和考研系统联调；调通以后，统一私有化部署到需求方的云服务器上。

## 10. 需求方要准备的

- 考研系统的接口规范（开工时提供）；
- 正式部署用的云服务器；
- 云端大模型的账号（base URL、API Key）；
- 用于开发和验收的空白答题卡、填好的样卡。
